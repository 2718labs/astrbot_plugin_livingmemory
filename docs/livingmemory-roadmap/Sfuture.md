# Sfuture：远期记忆能力愿景

本文件只记录尚未立项的独立愿景：非破坏性聚合、矛盾检测与消解、可选的 rerank 层、动态路线选择、结构化时间与时间检索、topic 候选生成（动态词表规模化），以及用户偏好画像提炼。

它们都属于新增能力，不是当前 S0-S6 的链路修复，也不自动成为 S6 的后续任务。是否实施、何时实施、采用什么数据结构，都必须在主线稳定后重新调查和立项；当前阶段不得为它们预埋空状态、空表、后台任务或无消费者接口。

## 与当前主线的边界

以下能力仍属于 S0-S3，不能因为聚合愿景后置而取消：

- 同一来源窗口重试只写入一次。
- 完全相同或能确定为同一输入的结果不重复落库。
- 同一个 topic 在名称、scope 和身份确定一致时复用同一节点。
- 每条事实只建立自身有直接来源证据的关系。

以下能力全部留在本文件，不进入当前执行计划：

- 跨多条历史记忆发现语义簇。
- 从多个具体事实综合出更高层主题或长期结论。
- 合并近义 topic、alias 或记忆正文。
- 判断新旧事实是否矛盾，以及决定并存、替代、失效或撤销。
- 为事实建立独立时间对象，或按“最近、上次、某段时期”等自然时间条件检索和排序。
- topic 规模超过全量候选列表上限后的检索式候选生成（愿景六）。
- 从同一人物的多条父记忆及其事实中提炼、更新可复用的偏好画像（愿景七）。

## 愿景一：非破坏性聚合

### 定位

聚合不是“认出两个输入是同一个 topic”，而是从多条已经合格、彼此独立的记忆中产生一条新的上层综合结果。它应作为独立 Feature Request 评估，不能混入 S1 的产物契约、S2 的统一处理链或 S3 的节点归一。

### 初步方向

- 优先生成派生的上层主题或综合记忆，不直接覆盖、删除或改写来源记忆。
- 每条聚合结果必须保留完整来源集合，撤销聚合后原记忆仍然可用。
- 聚合是否进入召回、以什么权重进入、是否替代来源正文，必须由真实消费者和评测决定。
- 不以减少记录数量为目标，也不允许重新制造包含多个无关主题的混合大文档。
- 当前默认关闭的 Consolidation 及其实例负例只作为调查材料，不作为未来实现基础。

### 立项前必须回答

1. 用户侧具体收益是什么：减少重复、形成长期主题，还是帮助图谱联想？
2. 聚合结果的唯一消费者是谁？
3. 候选如何形成，怎样避免把“相关”误当“相同”？
4. 原记忆与聚合记忆同时被召回时如何避免重复注入？
5. 如何撤销、重算并解释每条综合结论的来源？
6. 固定评测集能否证明它比稳定节点复用带来额外净收益？

### 可能顺序

如果未来获准立项，应先评估只读候选和派生聚合，再决定是否影响生产召回；不得从自动合并或历史改写起步。

## 愿景二：矛盾检测与消解

### 定位

矛盾检测与矛盾消解必须分开看待：检测只是提出候选，消解会改变系统认定的事实、状态和后续召回。尤其是消解，足以作为独立 Feature Request 和大版本候选，不能作为普通优化顺手加入。

### 为什么风险更高

- 不同时间、主体、条件和语境下的不同说法可能都成立，并不一定矛盾。
- 一条新信息可能是补充、阶段变化、临时例外或真正否定，处理动作完全不同。
- 错误聚合通常还能保留来源；错误消解却可能让正确事实退出生产召回。
- `SUPERSEDED` 只有真正改变主线消费者时才有意义，不能再次成为有状态、无消费者的悬空机制。

### 立项前必须回答

1. 只做矛盾候选提示，还是允许系统自动改变事实状态？
2. 事实的主体、时间、条件和来源是否已经稳定到足以比较？
3. 哪个消费者读取“并存、被替代、已失效”等状态？
4. 检测错误和消解错误分别怎样衡量、撤销和复核？
5. 写入时检查与周期补漏各自解决什么问题，是否真的需要两条触发路径？
6. 这一能力是否值得改变版本契约、数据库结构和召回语义？

### 可能顺序

如果未来获准立项，应先建立只读矛盾候选和评测，再单独决定是否建设消解；检测通过不等于自动替代获得授权。

## 前两个愿景之间的关系

聚合通常比矛盾消解更容易做成可撤销的派生层，因此如果两个愿景都获准立项，可以优先调查聚合。但二者不是当前路线的连续阶段，也不存在默认承诺：聚合完成不代表必须继续做矛盾消解。

## 愿景三：可选 rerank 层

### 定位

当前没有独立 rerank 层只是能力现状，不是已经证明的缺陷。只有 S5 的事实级候选、拒绝机制和预算装配稳定后，才有干净基线判断“再排一次”是否真的改善最终注入。

### 初步方向

- rerank 的唯一位置是：事实候选形成之后、最终相关性拒绝与预算装配之前；它不能回头修复坏写入、错误 fact 或全组合图边。
- 不预设必须使用 LLM、cross-encoder 或某种固定模型；先比较现有排序失败样本需要的判断能力、延迟和运行成本。
- rerank 必须保留候选原始路线信号和自己的重排理由，不能用一个新分数覆盖全部可解释信息。
- 如果现有事实级检索已经满足 Stest，保持没有 reranker 也是合格结论。

### 立项前必须回答

1. 它具体修复哪些 S5 后仍然存在的排序失败，而不是泛泛追求更智能？
2. 重排候选池多大，额外延迟和模型调用成本是多少？
3. 它是否改善最终注入和成对盲测，而不只是改变候选池名次？
4. 对负向和模糊查询，它会更敢拒绝，还是反而把低质量候选包装得更可信？
5. 失败、超时或模型不可用时是否能稳定退回 S5 已验证的基础排序？

### 可能顺序

未来若获准立项，先离线重排 S5 固定候选并做消融；只有最终事实命中、负向注入、自然使用体验的净收益足以覆盖延迟和成本，才接入生产链。

## 愿景四：动态路线选择

当前 `dynamic_route_weighting` 已改为默认关闭，显式开启仍保留原行为。现有实现会同时查询 document/fact 与 graph，再按关系词、时间词和事实词改变融合权重；它没有节省查询成本，也没有证明比固定权重更可靠。

未来若重新立项，必须先有通过 S5/Stest 的固定权重基线，再判断查询意图、候选可信度或路线拒绝能否带来稳定净收益。验收看最终注入、负向样本和延迟，不以“权重发生了变化”作为成功；无法稳定胜出时继续默认关闭。

## 愿景五：结构化时间与时间检索

### 当前决策

当前主线不建立独立 `fact.time`，也不实现按时间过滤、排序或自然语言时间检索。总结模型能看到每条消息的发送时间：对本窗口中发生、说出、确认或形成的事情，在 fact 正文中固定写出具体日期，时段则按消息时间自然表达（如凌晨、早晨、上午、中午、下午、傍晚、晚上、深夜），不限定固定词表；“今天、昨天、明天、下周”等相对表达也以对应消息时间为基准改写。若事实明确描述另一个时刻发生的事件，则保留事件时间，不拿消息发送时间冒充；消息发送时间仍作为来源窗口元数据保存。

### 为什么后置

“时间”不是一个单值标签，至少可能指事情发生时间、说出时间、开始或结束时间、截止时间、持续区间和周期。查询中的“最近、以前、上次”又会随查询当天变化；新的记忆变旧后，同一句查询的正确候选和排序也可能变化。把这些差异压进一个由总结 LLM 自由填写的对象，只是把问题藏进字段里，不能证明系统理解了时间。

结构化时间还必须有明确消费者。当前 fact 级语义/词面检索已经能使用正文中的具体日期；在没有固定时间查询样本和收益证据前，额外字段会扩大输出契约、增加整批写入失败面，并诱导系统把“消息发送时间”误当“事情发生时间”。因此它与跨记忆聚合、矛盾消解一样，必须作为独立 Feature Request 调查，而不是 S1 的基础字段。

### 立项前必须回答

1. 先支持哪一种时间问题：精确日期过滤、事件区间，还是“最近/上次”的自然问法？
2. 需要区分哪些时间语义，谁负责把时间绑定到正确事实和条件？
3. 相对时间以哪条消息、哪个时区和哪个查询时刻为基准？
4. 事实正文中的绝对日期为什么不足，结构化字段的唯一消费者是谁？
5. 时间过滤与语义相关性冲突时谁优先，旧但关键的事实会不会被错误压低？
6. 如何用跨天、跨月、周期、截止、持续和无时间事实组成固定评测，而不是靠几次模型输出判断成功？

### 可能顺序

未来若获准立项，先从不调用 LLM 的精确日期/区间消费者和只读评测开始，再决定是否需要结构化写入；自然语言时间理解与动态排序必须单独立项。不得提前在当前 fact 契约中预埋无消费者字段。

## 愿景六：topic 候选生成（动态词表规模化）

### 定位

当前总结 prompt 把当前 scope 的全部 topic 名作为候选列表发给 LLM（"可复用候选"），由 LLM 复用或新建；系统侧用字符级规范化 + 精确匹配兜底去重。这个形态在小规模（几十个 topic）下成立，但列表随规模线性膨胀：topic 数百上千后，全量列表既塞不进 prompt，LLM 也看不完，退化为"发一本没人看的词典"。本愿景把"全量列表"升级为"按需检索 top-K 候选"，让候选长度恒定、规模无关。

### 初步方向

- 候选生成三件套（按优先级）：
  1. **词面检索（主力）**：用当前窗口的消息文本做 FTS/BM25 命中旧 topic 名——消息里出现"考研"即召回旧 topic"考研准备"。零模型调用，SQLite FTS5 自带 BM25 排序，可直接复用既有全文检索基建。
  2. **消息级向量兜底**：每条消息（或几句话一组）单独向量化，与 topic 名向量比相似度，处理"没提关键词但语义在聊同一话题"的情况。注意 topic 名过短、向量质量一般，只作兜底不求完美；embedding 调用按消息数计，有成本。
  3. **高频统计兜底**：检索结果不足时补最近最高频/最近使用的 topic（纯 SQL 统计）。依据：能被复用的 topic 往往本来就常聊，"与苦杏的关系"这类高频话题即使这轮措辞对不上检索，也能被捞进候选。
- 触发条件：scope 内 topic 数超过阈值（暂拟 50–100）自动从全量列表切换为检索子集；阈值以下维持现状。
- 检索不到的正确语义是"新话题，LLM 新建"——这是期望路径而非失败；检索漏掉该复用的候选最多产生一个碎片，由愿景一的后台合并兜底。
- 与愿景一的分工：本愿景是**写入端防碎片**（让 LLM 更可能复用旧名），愿景一是**后台收碎片**（把已产生的近义碎片归并）；二者互补，不在本愿景内实现合并。

### 候选生成执行链（实现方式）

分层顺序固定，每层只负责"补足到 K"，不做二次过滤（词面命中即算数，不因向量分低丢弃）：

```text
窗口消息（本轮对话原文）
  → ① 词面检索：消息文本 FTS/BM25 命中旧 topic 名
       ├─ 命中 ≥ K 个 → 取 top-K 直接作为候选
       └─ 命中不足 K 个 → 进入 ②
  → ② 消息级向量兜底：消息文本向量 vs topic 名向量，取相似度最高且未入选者补足至 K
       ├─ 已补足 → 候选完成
       └─ 仍不足 → 进入 ③
  → ③ 高频统计兜底：scope 内按使用频次/最近使用排序，取未入选者补足至 K
       └─ 候选完成（可能仍少于 K）
  → 候选列表（≤ K 个，K 暂拟 20）拼入总结 prompt
       └─ 候选为空（三层零命中）→ 不附候选列表，LLM 自由新建（期望行为）
```

- 执行链无硬失败：三层全零命中 = 新话题，走"新建"分支，不算错误。
- 每层产出与上一层取并集，顺序只决定补足顺序，不丢弃已命中的候选。
- 成本：词面层零模型调用；向量层按消息数计 embedding 调用（可退化：词面有命中时跳过向量层，只在该层零命中才启用）；高频层纯 SQL。
- 候选列表始终 ≤ K 条且按层优先排序展示（词面命中在前，便于 LLM 优先看到字面相关的旧名）。

### 为什么后置

当前单 scope 短周期样本（26 facts / 7 topics）全量列表完全够用，检索子集是在为不存在的问题造轮子。是否真的需要、需要多大规模时才需要，应由部署实机后的 topic 数量/重复率数据决定。

### 立项前必须回答

1. 真实数据下 topic 数达到多少时，全量列表开始失效（LLM 无视候选、token 膨胀、复用率下降）？
2. 词面命中能覆盖多少真实复用场景；消息级向量兜底的额外成本（embedding 调用）是否换来可观测的复用率提升？
3. 检索漏掉该复用的候选时，新建碎片率上升多少；愿景一的合并能否兜住，还是需要更硬的写入端约束？
4. 高频统计兜底会不会把与当前窗口无关的高频 topic 混进候选，干扰 LLM 判断？
5. 切换阈值按 scope 还是全局；不同规模用户如何平滑迁移，不出现"昨天还能复用、今天列表变了"的割裂？

### 可能顺序

如果未来获准立项，先做纯 SQL 的词面层 + 高频层（零新依赖、零模型成本）并对比复用率；消息级向量层只有词面层证明不够时才加入。不得一开始就上全三件套。本愿景不包含近义合并，合并仍归属愿景一。

## 愿景七：用户偏好画像提炼

### 定位

偏好不是另一种原始记忆，而是用户画像中的派生层：它回答“这个人在特定场景下通常更倾向什么”。来源是同一人物的父记忆及其旗下事实条目；父记忆提供完整语境，事实条目提供可聚合、可追踪的证据。偏好结果不得覆盖或改写来源记忆。

### 初步方向

- 每条偏好保留人物、适用场景、倾向内容、强度、置信度、正反证据、来源 parent/fact ID 和最后更新时间。
- 明示偏好（如“以后都用简短回答”）可以由单条明确证据形成；从行为推断的隐式偏好必须由多条、跨时间证据逐步形成。
- 同名人物只在身份确定一致时聚合；身份不确定或同名冲突时不猜。
- 新证据可以增强、削弱、限定或推翻旧偏好；来源归档、删除或修正后，相关偏好必须可重算。
- 偏好只作为回答和行为选择的参考，不能把一次选择、玩笑、临时情绪或单次例外固化成用户定性。

### 为什么后置

当前 fact 已能保存用户明确说出的偏好；本愿景要解决的是跨记忆归纳和持续更新，属于新的派生状态与消费链。若没有证据门槛、反例处理、重算机制和明确消费者，它只会把模型猜测包装成“画像”。因此不得混入当前总结调用，也不得预建无消费者的偏好表。

### 立项前必须回答

1. 第一批消费者是谁：回答风格、内容推荐、工具默认参数，还是主动行为？
2. 哪些偏好允许单条明示证据成立，哪些必须由多条隐式证据形成？
3. 偏好的 scope 如何与平台人物身份、persona 和会话范围对应？
4. 反例、临时例外和真实偏好变化分别怎样区分、衰减和撤销？
5. 父记忆与 fact 同时作为输入时如何避免把同一证据重复计数？
6. 如何证明画像带来的命中收益高于误判、标签化和额外注入成本？

### 可能顺序

如果未来获准立项，先做只读候选：按人物聚合父记忆和 fact，输出带完整证据引用的偏好建议，不进入生产提示词。固定评测证明稳定后，再决定偏好状态如何更新以及由哪个消费者读取。

## 当前状态

- 非破坏性聚合：Vision，未立项。
- 矛盾检测与消解：Vision，未立项；消解属于大版本候选。
- 可选 rerank：Vision，未立项；是否需要由 S5/Stest 的剩余失败样本决定。
- 动态路线选择：Vision，当前默认关闭；未来须重新证明固定权重之外的净收益。
- 结构化时间与时间检索：Vision，未立项；当前只在 fact 正文固定具体日期、自然描述时段，并保留来源时间。
- topic 候选生成：Vision，未立项；当前维持全量候选列表，等实机数据决定是否需要、何时切换到检索子集。
- 用户偏好画像提炼：Vision，未立项；来源限定为同一人物的父记忆及其事实，先做可追溯的只读候选。
- S0-S6 与 Stest：不得引用本文件作为新增实现范围或验收条件。
