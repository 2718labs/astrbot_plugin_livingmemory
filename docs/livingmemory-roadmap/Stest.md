# Stest：整体验收与改造净收益判断

目标：回答“这次改造究竟变好了没有”，并能指出任何失败属于写入、存储、图、事实层、召回、注入还是生命周期，而不是全部走完后只凭几次聊天的主观印象判断。

Stest 是最后一个验收节点，但验收不是到这里才开始。S0 先保存改造前生产基线；S1-S6 每阶段在实现前固定失败样本、完成后通过本阶段门槛；Stest 只冻结版本、汇总证据、跑完整链路和真实体验盲测。若失败，退回拥有该契约的阶段修复，不在 Stest 临时加过滤器或提示词补丁。

历史尺度来自旧调查文档 `memory-system-analysis.md` 第 8b 节对长期正确、自然使用、可审计和可纠错的定义。本阶段只验收 S0-S6 已获准范围；跨记忆聚合和自动矛盾消解仍属 `Sfuture`，因此即使 Stest 通过，也不宣称已经完成自动自我纠错。

## 验收结构

```text
实现前：冻结本阶段失败样本和比较口径
  ↓
每阶段结束：局部回归 + 结构不变量 + 性能记录
  ↓
Stest：同一原始消息完整重放 → 最终注入 → 成对回复
  +
时间压缩回放：写入 → 衰减/归档 → 重启/rebuild → 再召回
  ↓
通过 / 退回责任阶段 / 保持某条可选路线关闭
```

## Stest-01：先冻结判卷方式

- 记录 baseline commit、candidate commit、配置快照、fixture 版本、数据库 schema 版本、embedding/tokenizer/模型版本和随机种子；报告不能脱离这些信息单独流传。
- S0 的正向、负向和生产顺序基线继续作为主样本；各阶段新增的失败样本只能在看到最终结果前登记，不能为让 candidate 通过而删除旧样本。
- 在最终运行前锁定哪些指标属于硬门槛、哪些只作观察。具体比例由 S0 基线和第一轮人工标注校准，不在路线图里凭感觉预写。
- 同一份原始消息、查询和当前上下文分别跑 baseline 与 candidate；不能拿旧文档候选池和新事实最终注入直接比较。

## Stest-02：写入与存储整链验收

- 从原始消息开始触发 `store / skip / invalid`，检查最终 parent、facts、索引、图 evidence，以及 S4 选定的唯一事实层。
- 人工标注窗口是否值得长期保存、应产生几条中心记忆及其必要事实；分别报告误写、漏写、编造、混合事实和来源断链。
- `skip` 必须推进滑窗且零写入，`invalid` 必须保留重试边界且零 active，下游失败不得留下可搜索半成品。
- 在线写入与从同一 canonical 数据 rebuild 后，parent/fact/index/graph 的规范签名必须一致。

## Stest-03：最终召回与注入比较

- 正向查询检查目标 fact 是否进入最终注入，不只检查候选池；同时记录 Hit@1、Hit@3/最终 k、MRR 和事实正确率。
- 负向与模糊查询检查是否返回空或最小必要事实；单独报告 negative injection rate、无依据 fact 和错误 recent 进入率。
- 记录候选 fact 数、最终注入 fact 数、注入 token、p50/p95/最大延迟和失败率；任何路径都不得突破 S5 硬预算。
- 固定多事实 parent 样本，确保命中一条 fact 不带出 sibling facts、整篇 summary 或重复元数据。
- 图路线只有在 S3 数据价值与 S5 融合回归均通过后参加 candidate；若没有净收益，图权重保持 0 也可以通过 Stest。

## Stest-04：时间压缩与规模收敛

- 使用可控时钟重放一段被压缩的长期使用过程：有价值事实、无价值窗口、事实被召回、时间流逝、衰减/归档、重启和 rebuild。
- 观察 active facts、可搜索索引、孤儿来源/图 evidence、失效事实误召回和注入 token 是否随时间失控；区分正常新增的高价值事实与链路污染，不能只看记录总数下结论。
- 已归档、过期或遗忘的事实必须按 S4/S6 选定语义真实退出生产召回，父文档和旧索引不能绕过状态。
- 同一数据在重启和 rebuild 前后应保持等价；时间任务重复执行不得造成二次衰减、重复归档或悬空索引。
- 这项测试不模拟尚未立项的自动矛盾消解；遇到新旧事实冲突时只验证当前已声明行为，不把 `Sfuture` 当隐藏验收条件。

## Stest-05：体验不是随便聊几句

- 用相同当前上下文分别生成 baseline 与 candidate 回复，随机交换 A/B 顺序并隐藏版本信息后再评审。
- 评审只看五件事：事实是否正确、是否真的帮助当前回答、是否自然、是否主动宣布/复述记忆、是否遗漏用户明确追问的旧事。
- 同时包含“应该使用记忆”和“应该保持沉默”的成对场景，防止防复读规则把系统改成不敢使用记忆。
- 实际连续使用观察只作为最后一层外部有效性确认；它不能替代前面的固定样本，也不能用偶然的一次好聊掩盖确定性回归失败。
- 保存每个分歧样本及理由。不能仅用一个总分覆盖“搜错了”“注入错了”和“表达不自然”三类问题。

## Stest-06：通过规则

- 任一 P0 固定回归失败，整体不通过并退回对应阶段。
- candidate 必须通过所有写入/结构硬不变量，最终注入不得超预算；正向事实正确率不能出现未事先接受的退化。
- 体验盲测用于判断净收益和发现自动指标未覆盖的问题，但不推翻确定性的来源断链、错误事实、负向注入或预算超限。
- 图、Atom、生命周期反馈等可选机制各自判定；没有收益时保持关闭或采用简单方案，不为了让路线图显得完整而强行启用。
- 最终报告逐项列出 baseline、candidate、变化、失败样本和责任阶段，结论只能是 `通过`、`退回某阶段` 或 `核心通过但某可选路线保持关闭`。

## 完成条件

- [ ] 评测 manifest 足以重放同一 baseline 与 candidate。
- [ ] 原始消息到最终注入的完整链路已在干净数据库上运行，而不是拼接各阶段单测结果。
- [ ] 写入、召回、预算、延迟、长周期和体验结果均有独立报告，失败能定位到责任阶段。
- [ ] 时间压缩回放后没有可搜索半成品、孤儿索引、状态绕过或无界 token 增长。
- [ ] 成对盲测同时证明相关记忆能自然使用、无关记忆能保持沉默。
- [ ] 最终结论没有临时改变门槛，也没有把 `Sfuture` 能力冒充成当前完成项。
